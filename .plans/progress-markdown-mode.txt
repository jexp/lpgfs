## TASK-013 — 2026-07-22T22:07:00Z
Resolved the type-key clash rule: label wins the `type` frontmatter key (preserving REQ-F-021's "always includes type: <Label>" invariant), and a literal `type` property colliding with it is demoted to a `type_property` key so both values survive without silent data loss. Locked in the full frontmatter key-order contract with a dedicated exact-string ordering test.
Files: ~src/markdown/renderer.ts, ~src/markdown/renderer.test.ts, ~.plans/tasks-markdown-mode.yml
Decisions: chose "label wins, property demoted to type_property" over "property wins, label demoted to label:" because it keeps `type` always equal to the label — the stronger consistency guarantee for downstream OKF/Obsidian tooling that assumes `type` is the label. Key order is: type, type_property (only when a clash occurred), title, timestamp, tags (fixed order, not alphabetical), remaining properties (alphabetical), relationship keys (alphabetical, in_<TYPE> included). A `null`/absent `type` property is not treated as a clash. The rare double-collision case (a node with both a colliding `type` property and a genuine `type_property` property) is an accepted, documented, unhandled edge case — the demoted value overwrites it rather than being silently ambiguous.
